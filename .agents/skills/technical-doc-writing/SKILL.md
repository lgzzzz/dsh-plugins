# 通用技术文档与文案写作标准

## 这份技能是做什么的

这份技能回答一个简单的问题：**一段文字该不该写、写多少、怎么写才清楚。** 它适用于任何项目的技术文档和文案——README、Markdown 文档、JSDoc、代码与测试注释、提示词、技能描述、诊断信息、CLI/UI 文案等。

目标：让每一页文档既容易搜到、又对新人友好，同时对智能体和维护者足够精确。

全文围绕三个核心观点：

1. 文档只写“**现在是什么样**”，不写“过去改了什么”。
2. 每条事实都**只有一个权威来源**（由谁来负责解释它）。
3. 删减文字的前提是：**必须保留的事实一条都没丢**。

这份技能是“判断和取舍的指导”，不是可以逐条照抄的脚本或清单——它教你怎么思考，而不是给你现成答案。

## 先认识几个词

这些词会反复出现，先看懂再往下读。

- **约定**：读者、调用方或维护者**依赖的硬性事实**（不能随便改的那种承诺）。例如“这个函数可能抛异常”“这个配置默认关闭”“这件事必须在 B 之前完成”。删减时最不能丢的就是约定。
- **来源 / 出处**：某个事实的**权威出处**。例如 API 的行为由代码和类型定义负责，完整的清单由生成器负责。改一个事实，要先改它的来源，再改引用它的地方。
- **自动生成的文件**：由别处**自动生成**的文档或快照，不能手工改，只能改源头后重新生成。
- **事实主张**：一个能判断真假的说法（例如“该函数可能抛异常”）。全文说“事实”或“主张”时，指的就是这类说法。
- **反事实现在时**：写一个修复时，用“**如果没有 X，就会发生 Y**”，而不是“以前会 Y”。例：写“没有空指针检查时，空输入会崩溃”，而不是“以前空输入会崩溃”。
- **思维链泄漏**：文字里残留了“**写作过程**”的痕迹——引用了只有那次写作会话才看得到的草稿编号、评审对话、PR 顺序等，而不是站在成品仓库的角度说话。
- **自动 / 交互模式**：自动模式直接改、只报告真正的难题；交互模式在难题处给你几个选项。它只决定“**要不要问你**”，不决定“**能不能改**”。

## 约定的完整性：删之前先确保要保留什么

动手改一段文字前，先把里面每一个“**事实主张**”找出来，并保留所有相关的：

- 谁做了什么（主体 + 动作）；
- 在什么条件下、什么时机、什么顺序；
- 表示“必须 / 可以 / 绝不”的词（英文 must / may / never）；
- 否定的保证与例外；
- 副作用、谁负责、失败会怎样、后果是什么。

只有当**一个事实子句都没丢、而且结果确实更清楚**时，才去删形容词、重复和叙述性的废话。**字数变少本身不是进步。**

约定要完整地放在“**使用点**”——也就是调用方或维护者当场需要看到的地方。架构、原理、算法、历史、扩展示例这些背景内容，链接到来源文档即可，不必就地复述。同一个事实只在它的来源文档里解释一次，但关键的约定可以在使用点重复一次（因为那里是读者最需要它的地方）。

## 一个事实一个来源：每个事实只有一个权威出处

源码、测试、生成目录、README、指南、决策记录，各自负责自己那一类真相。更新顺序永远是：**先改来源，再改自动生成的文件。**

生成目录和快照要当作“自动生成”处理：动手前先找到所有用到它的地方，改拥有它的源头（例如源码里的 JSDoc 或生成器模板），再重新生成所有自动生成的文件。

## 当前状态：只写现在，不写“以前”

普通文档只描述**当前**的代码和行为。“以前是……现在改成……”这种变化叙述，只该出现在变更记录、升级指南或复盘里。

写一个修复时，用现在时的反事实说法——“**没有 X，就会发生 Y**”——而不是讲仓库历史“以前会 Y”。

## 页面顺序、深度与粒度

1. 页面按固定顺序：元数据 → 标题 → `Summary`（概述）→ `Table of Contents`（目录）→ 用户面向内容 → 开发者面向内容 → 可选的 `Further Exploration`（进一步探索）→ 末尾 `Dev Note`。
2. 每个实质性章节开头，用一小段话说明“这节讲什么、读完能做什么决定”，再进入表格、代码或子章节。
3. 内容按深度从浅到深：基本用法（何时选它、要什么输入、最短安全示例、怎样算成功、失败了怎么恢复）→ 高级用法（配置选项、限制、操作、集成行为）→ 开发者细节（所有权、生命周期、数据模型、失败、性能、安全、值得维护的扩展点）。
4. 把重型的开发者细节折叠起来（例如 `<details>`），只写概念层面的说明——整体设计、组件架构、数据流——具体精确的细节链接到代码。不要写成一份完整的罗列（API 清单、逐列罗列、把注释复述一遍）。
5. `Further Exploration`（进一步探索）：给出 3–7 个直接相关的链接，按“最近的前置知识 → 更深的探索”排序，每个链接用一句话说明它补充什么；不要做成全站索引。
6. 小规则文件：一条能被独立搜索的规则、实践或决定，单独放一个文件（前提是它有独立的来源、变更节奏、入链或校验）。紧耦合的规则就放一起，别让一条约定需要开好几个文件才能看懂。索引页用 3–5 句说明这个文件夹，并链接直接子项，不要复述子项内容。
7. 有些文件的形状不归文档作者管：工具自己读写的小文件、生成出来的片段、表头由解析器规定的格式（如 CSV 列头、frontmatter 必填键）。这类文件按格式本身的要求写，不要硬套上面第 1 条的 Summary 和目录骨架。这类文件为什么不套骨架，要写在定义该格式的地方（schema、解析器、生成器模板），免得后来的人看成漏写又补回去。

## 概述（Summary）怎么写

概述用三到五句话、一个段落，说清：读者能做什么或观察到什么、为什么在意、主要的运作方式、以及最重要的边界。

它描述的是“**能做什么**”，而不是“它是什么 / 内部身份”。凡是读者不会在配置、命令或公共 API 里直接用到的内部标识符，都省略。目录只做导航，不做描述。

## 事实核查：实测，而非臆断

文档写的是“产品**今天**的行为”，对任何操作类主张，唯一可信的证据是“**真的运行过**”。

1. 写安装/使用指导前，先给对象分类：读事实（包元数据、入口文件），而不是看文件夹名或凭类比猜。
2. 对着当前代码，逐条运行文档将要展示的命令、配置和示例，只写下实际观察到的输出、警告和失败方式。
3. 删掉无法复现的内容：绝不凭记忆、类比或相邻模块的文档去搬命令、字段、默认值或行为。
4. 修订旧页面时，先和最新上游比对；上游里已经过时的陈述，仍要按代码纠正，而不是按旧文字纠正。
5. 依赖密钥或网络、无法亲自核实的，就注明“由谁负责验证”，而不是直接断言行为。

## 受控技术英语

对需要被智能体、译者或非母语读者解析的英文，做一轮“**受控技术英语**”（受 ASD-STE100 启发）审查。这是一套清晰度纪律，不是认证合规。

- 说清主体和动作；主体重要时用主动语态。
- 一个概念固定用一个术语，不要为了求变化而换同义词。
- 优先用直接动词，替换名词化和含糊的短语动词。
- 一句话只放一条指令；三步或更多步骤/条件，用列表。
- 拆开分号和过长的从句链；每段只谈一个主题。
- 删掉没有依据的品质形容词和堆叠的模糊措辞；来源里的每一个事实和不确定程度都要保留。

把“指令 20 词、描述 25 词”当作**审查提示**，而不是硬性门槛——如果拆分会把条件或关系藏起来，就保留长句。绝不要为了凑长度而删掉或加强 must / may / never / 时机 / 例外 / 数字这些约定词。

中文同理：显式主体、一词一义、一句一指令，保留“必须/可以/绝不”这类限定。

## 页面排版

- **分节：** 用 `-----` 水平线分隔页面的主要部分，前后各留一个空行；不要把水平线直接跟在段落后面（会被解析成 Setext 标题）。
- **折叠：** 把开发者细节和末尾的 Dev Note 折叠进 GitHub 原生的 `<details>` / `<summary>`；标题（H2/H3）和锚点保持可见，只折叠标题下面的内容。块内 `<summary>` 后留空行、每行顶格（缩进会变成代码块）、内容和 `</details>` 之间留空行。折叠内的标题、列表、表格、链接照常解析。
- **强调纪律：** 加粗只用于“改变行为的那句”或“关键的比较”；表格里加粗表头和每行的最佳值。不要用强调来装饰。

## 不同位置各写什么

这一节不是让你一味删短。原则是：**当代码、类型和结构本身无法表达下面的约定时，就补写；当这些事实已经显而易见时，就不要为了加注释而加注释。**

- **公开 API / JSDoc：** 写清调用方可见的返回区别、抛异常或拒绝、副作用、所有权、时机、取消、持久性。
- **内部注释：** 解释非局部的结构和明显复杂的局部结构，包括不变量（始终不变的条件）、竞态顺序、所有权、安全边界、意外的失败行为；删掉控制流叙述和代码复述。
- **模块注释：** 说明模块的角色、依赖、职责和不明说的架构选择，并把架构选择链接到它的来源解释。
- **测试：** 只解释不明说的测试设计——为什么需要这个夹具、断言、平台适配、真实入口路径或间接观察。删掉走读和清单。
- **README：** 包含使用者的约定：配置、语义、失败、限制、扩展点和对外可见的效果。链接生成目录和跨模块来源，保留持久的缺口和维护者陷阱。
- **教程 / 手册：** 包含前置条件、必需动作、真实入口路径、可观察的验证方式和简明警告。
- **复盘：** 保留事件序列、证据、因果链、影响和预防；删掉重复的说服、以及和因果无关的实现细节。
- **技能与智能体指令：** 写清行为边界和显式的范围限制（例如“指导，而非脚本/清单”），工作流保持简洁并链接真正的来源。
- **示例与配置注释：** 解释访问限制、不明说的接线或加载顺序、安全立场、重放行为、例外和可能的误用；不要复述配置已经显示的内容。
- **提示词与可见字符串：** 把措辞当作行为（见下一节）。
- **诊断 / 报错：** 说明失败的主体或路径、违反了哪条规则、以及（不明显时）怎么纠正；删掉内部执行过程的叙述。

## 把措辞当作行为

模型看得见、或用户看得见的文字改动，就是一次**行为改动**：提示词、诊断文案、CLI 输出、UI 文案、无障碍名称、工具提示、占位符、格式模板，都是。

UI 文案要放进**类型化的本地化字典**，通过本地化原语传给界面，而不是硬编码。改动措辞需要有一条支持它的运行时证据（对应的快照或测试），并在同一次改动里一起更新；如果授权范围里没有对应的场景，就保留原措辞、报告延期，而不是把它悄悄折成一次纯文案编辑。

## 思维链泄漏：把“写作过程”从成品里洗掉

思维链泄漏，指的是文字的视角还停留在“**写作会话**”，而不是“**仓库成品**”：它引用只有那次会话才看得到的产物、叙述“变更”而不是“状态”、或是在跟一个已经离开的评审者争辩。

**唯一测试：** 对一段可疑文字自问——**一个处于当前 HEAD、手里没有会话记录、PR 线程或未提交草稿的读者，能不能解析每一条引用、核实每一条主张？** 如果不能，就以仓库的视角把还活着的事实重述一遍，删掉其余。

### 泄漏分类

1. **死设计引用：** `(decision 7)`、`(audit C2)`、`§4.7`、阶段标签之类。如果这个决定有已提交的来源，就按名称和路径引用；否则删掉引用，把它的关键事实重述成能独立站住的话。
2. **栈 / PR 视角：** “本栈后续的 PR”“这个 PR 新增了”“上一个提交”。改写成已经交付的机制或扩展点；还没做的事移到 TODO 标记或 issue 引用。
3. **变更叙事与版本戳：** “以前”“不再”“旧的 X”，以及“v1”“本次”“今天”这类索引式标记。改写成当前行为。
4. **审查编排：** “评审中否决了”“评审者确认”“第 5 版草稿”。把还活着的决定和理由保留成普通事实，删掉“谁在什么时候说的”。
5. **面向评审者的自证：** “这个转换是安全的——它只是……”“这是对的，因为……”。改成陈述“让代码安全的那个不变量”；如果代码本身已经表明，就直接删掉注释。
6. **复述与推导记录：** 控制流叙述（“先 X，再 Y”）、测试走读、对显而易见分支的证明。删掉，只保留不明说的约定或不变量。
7. **模糊措辞与规划残留：** “现在应该够用”“暂时没问题”。升级为 TODO / FIXME，或改写成实际的边界；删掉模糊措辞。
8. **语言混入：** 在某种语言的段落里夹带另一种工作语言的片段。翻译或删掉。

### 什么不是泄漏（要保留）

- **issue 引用与 TODO 标记：** 在 HEAD 就能解析，任何表面都保留。
- **抑制理由注释：** lint/覆盖率忽略的理由、空 catch 的解释，是必需文案；改错理由就修，绝不删。
- **反事实现在时的修复说明：** “没有 X，就会发生 Y”。
- **实测边界：** “(实测：512 层嵌套约 0.15s)”——“实测”这个词承载着证据，不能删。
- **运行时新旧状态：** “旧连接排空后新连接才接受”是运行时生命周期，不是变更历史。
- **外部引用：** 外部标准章节、设计稿帧名等，本来就是设计成在仓库外解析的。

### 改过头的陷阱

删除任何内容前，先把该段的事实主张数一遍，并核对：有没有把“义务”翻成“背书”、把“假设”拔高成“已发布特性”、删掉真事实、或丢掉证据来源。修正不是一味删除。

## 质量与审查

**质量准则：**

- **简明：** 公共路径只放达成结果所需的事实；更完整的真相保持在一个链接或一层细节之外。
- **直观：** 前置概念先于依赖概念，下一步动作显而易见，标题用读者会去搜索的词。
- **友好：** 读者能认出“成功了”、能在行动前理解风险、能从常见的失败中恢复、能选择要不要继续深入。
- **准确：** 每条持久主张有且只有一个来源，并且有一条和它风险相称的验证路径。
- **智能体可读：** 元数据、稳定标题、锚点、术语、所有权、状态，都支持定向检索，不用加载全文。
- **新人可完成：** 一个没有仓库背景的专业工程师，能通过三到五页互相链接的页面，重建出相关架构或特性。

**新人测试：** 读者读完应能回答：它做什么、怎么安全地运行或使用、状态存在哪、哪个组件拥有它、它如何失败、以及在哪里改它。

**证据审查：** 每条实质性陈述，对照它最强的来源——用元数据核对名称和入口，用类型/JSDoc 核对 API 约定，用运行时代码核对行为，用测试核对被覆盖的失败路径，用生成目录核对完整清单。绝不要把旧文档、讨论或报告看得比当前代码和测试更权威。一条陈述只有在能帮目标读者行动、推理或避免误用时，才值得保留。

**字数预算（如果项目设了上限）：** 上限只是限制，不是削减目标。达到或低于目标时保留余量，别一达标就继续删；只有在内容确实需要这些字时才提高上限，并说明理由。

## 边界情况

只有当**一个事实主张有两个版本都满足“约定完整”、却在被接受的原则之间有所权衡、而且本技能没有明确裁决**时，才算边界情况。只有一个保留事实的答案的重写，不是边界。

模式只控制“**要不要问你**”，不控制“**能不能改**”：审查和审计任务只报告发现、不做编辑；明确授权的写入、修复或精简任务，才真正落地修改。

- **自动模式（默认）：** 有授权就应用清晰的编辑，把真正的疑难报告出来而不发问；不要为了推进而削弱事实。
- **交互模式（你显式要求时才进入）：** 把同类段落按主导原则分组，给你两到三个可行版本并推荐一个，说明它们在事实或结构上的差别；不要给劣质的干扰项。

你做出决定后，把这条规则应用到范围内所有同类段落。项目若已有校准样例文件（“原则 + 选定版本”的沉淀处，路径由项目指定），把结论追加进去，且不要带 PR 历史或评审叙述。

## 排除项

下面这些永远排除在文案的发现、审查和编辑之外，即使你要求范围是“整个仓库”：

- 生成目录与快照等自动生成的文件（改来源后重新生成）；
- 夹具等数据文件（按数据本身维护，不做文案润色）；
- 第三方 / 依赖 / vendor 代码；
- 归档 / 冻结的历史快照（只用来理解历史引用，不现代化它的文字或出链）。

## 工作流

1. 确认范围（scope）、模式（自动 / 交互）、当前分支或基线，以及适用的规范文件。**范围缺失时，报告所需输入并停止——不要自行推断“整个仓库”，也不要开始面谈。**
2. 先读来源，再判断一段文字。
3. 检查请求范围内的内容，而不是只看最大的文件；用搜索和字数统计找候选，再逐段做语义判断。
4. 把每个候选归类为：保留 / 新增 / 精简 / 恢复 / 重构 / 延期。只有任务授权编辑时才落地修改；不要为了凑一个删除目标而制造编辑。
5. 先更新来源，再更新自动生成的文件；学到新规则后，复查同类段落。
6. 运行最小相关检查，并复核最终差异里不含排除项路径。
7. 报告：检查过的范围、应用的清晰修改、刻意保留、延期项，以及实际运行的检查。
