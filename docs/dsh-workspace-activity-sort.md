# dsh-workspace-activity-sort

左侧栏里**最近有会话活动、或正在等用户处理的工作区自动浮到最前**，并且**某个工作区被排到第一位时，左侧栏的工作区列表自动滚回最上面**。谁该在最前由宿主自己的事件决定：用户消息提交（`api-session/activity`）、任务完成、模型请求重试耗尽后的报错，以及会话开始等用户（工具审批、提问、计划确认）。顺序写回 Workspace 注册表的持久显示顺序，所以重连的客户端、第二个 GUI、桌面端看到的是同一份顺序；它只上浮被激活的那一个，不做全量重排，挂载之前发生的活动不会被追溯。滚动由浏览器半部完成：宿主只写顺序，浏览器跟随顺序，在第一名换人时把工作区列表送回最上面。

-----

## 它做什么

本节按使用者能观察到的现象列出全部行为。

- 在某个工作区里**发出一条用户消息**（新建会话后开始交互，或在已有会话里继续、steer），那个工作区立刻移到 Workspace 分组的最前。
- **任务完成**：该工作区的回合正常答完（有最终回复），工作区同样移到最前。
- **任务报错**：大模型请求重试到上限仍未成功、agent 因此停下时，工作区移到最前。
- **等用户处理**：某个会话发起**工具审批**（`approval/request`）、**提问**或**计划确认**（`user-questions/request`）时，它所属的工作区立刻移到最前——这条请求常常来自一个你已经切走的会话，上浮后它才回到左侧栏最前面。
- **滚回最上面**：有工作区被排到第一位的那一刻（宿主半部的上浮、别的客户端上的活动），左侧栏的工作区列表滚回顶部（树模式下第一名未必出现在第一行，见下文「边界」）。本地拖拽期间与刚结束时不滚，工作区分组不可见时也不滚，见[上浮后滚回最上面](#scroll-to-top)。
- 只动「活跃的那一个」：其余工作区的相对顺序不变——是上浮，不是每次全量排序。
- **平时不动顺序**：手动拖拽、改名、新建 / 删除工作区都原样保留，直到下一次会话活动或等待用户的请求。
- 顺序写回注册表的持久显示顺序(域全局单例的 `workspaceIds`，`registry.list()` 按它投影)，所以它是权威事实：浏览器通过 workspace 控制器 `follow()` 的 `order` 增量跟随，重连的客户端、第二个 GUI、桌面端看到的是同一份顺序。

## 触发时机

插件只订阅下表里的七个宿主事件，表外的事件一律不动顺序。

| 宿主事件 | 插件动作 |
| --- | --- |
| `api-session/activity`（用户消息提交） | 该会话所属的工作区上浮到最前 |
| `session/event` 的 `turn/end`（任务完成 / 模型请求重试耗尽） | 该会话所属的工作区上浮到最前 |
| `approval/request`（工具审批进入应答链） | 该会话所属的工作区上浮到最前；请求原样交还应答链 |
| `user-questions/request`（提问 / 计划确认进入应答链） | 该会话所属的工作区上浮到最前；请求原样交还应答链 |
| `session/created`（新会话，非 subagent 且还没归属） | 登记，等它落位 |
| `domain/changed`(workspace 域、`workspaces` 表) | 让登记的新会话认领工作区，认领到就上浮一次 |
| `session/disposed` | 作废还没落位的登记与重试记录 |
| 手动拖拽、改名、新建 / 删除工作区 | 插件不动顺序（顺序由注册表自己改）；浏览器半部单独看顺序变化决定要不要滚 |

登记的新会话等 60 秒还没归属就放弃(它可能不属于任何工作区，比如按 `cwd` 创建、没有登记为 workspace 的会话)。

### 任务终点的判定

`turn/end` 只是「回合结束」，不是每次结束都算任务终点。插件按下面的规则判定：

- **完成**：`reason.kind === 'completed'`，且这个回合跑过至少一个 step——有最终回复。没跑过 step 的空回合不算。
- **报错**：`reason.kind === 'error'`，且**模型请求重试已耗尽**——当前 step 的 `llm/retry` 已经排到上限（`retry >= maxRetries`），并且错误码不是 `UNKNOWN`、`TOOL_ACTIVATION_FAILED` 这类非模型请求的合成码。
- 重试按 step 计数：`step/start` 清空上一个 step 的记录，避免上一 step 的重试替下一 step 作证。
- 其余终止原因都不算：`aborted`（用户取消、hook 取消、父级取消、会话销毁）、`blocked`（策略阻断）、`max-tokens`（token 上限截断）、`interrupted` / `forked`（崩溃与 fork 的补记，本就不是实时事件）。
- 重试上限来自 provider 自己的 `retryPolicy`，默认 `normal` / `maxRetries: 5`；插件不写死数字，只比较事件里的 `retry` 与 `maxRetries`。`always` 模式不设上限，也就不会耗尽。

### 等待用户的判定

「等用户处理」就是请求正在应答链里找应答者，插件只听两条 waterfall：

- **工具审批**：`dsh-user-approval` 在把 `approval/asked` 写进会话日志之后派发 `approval/request`，应答链就是浏览器里的审批卡片。
- **提问与计划确认**：`ask_user_question` 与 `exit_plan_mode` 都经 `dsh-user-questions` 派发 `user-questions/request`；计划确认是带 `plan-review` 意图的那一种提问，和普通提问走同一条链。

插件在链上**只观察、不裁决**：调用 `next()` 把请求原样交给下游，应答者收到的参数与没有插件时完全一样，插件把应答链的结果原样返回。注册时带 `prepend`，排在真正的应答者之前——上游客户端的应答者命中后不会再调用 `next()`，排在它后面的观察者会被短路掉，观察不到请求。

判定只看「请求进入了应答链」：审批策略为 `never` 时上游在派发之前就拒绝，观察者收不到，所以不上浮；subagent 子会话与不属于任何工作区的会话没有可上浮的分组。

## 上浮后滚回最上面

浏览器半部只看一件事：客户端工作区控制器投影出来的顺序里，第一名是不是换成了一个「本来就在列表里、原本不在第一位」的工作区。是就把左侧栏工作区列表的滚动位置写回顶部（`scrollTop = 0`），让列表从第一个分组重新开始显示。

- **每个浏览器各自判断**：顺序变化由宿主广播给所有已连接的客户端，所以活动发生在哪个客户端、由谁上浮，打开的每个 GUI 都会各自把列表滚回最上面。
- **只看第一名**：其余位置的变化（工作区之间互换、末尾追加）不滚。
- **写入排到下一帧**：顺序增量到达时只订一帧（`requestAnimationFrame`），下一帧才读 DOM 并写 `scrollTop`。这样读到的是新顺序提交之后的侧栏，同一帧里连着的多条增量也只会滚一次。
- **滚的是工作区区块自己的滚动条**：`[data-sidebar-list-area]` 是 `WorkspaceBrowser` 的列表区块，展开态侧栏里负责滚动工作区 / 会话行的容器。侧栏 viewport 自己只把顶部导航滚走、不画滚动条，是另一条滚动轴，插件不动它。
- **断线恢复后的第一份顺序是基线**：控制器失联时把 `state` 置为 `loading`，恢复后整份投影替换；插件把替换后的第一份顺序当新基线，不滚。断线期间另一边造成的上浮不会在本机补一次滚动。
- **本地拖拽静默**：从工作区分组行开始的拖拽，期间与结束后 `DRAG_GRACE_MS`（300ms）内不滚。拖拽本身会触发侧栏边缘自动滚动，把某一行拖到最前时它已经在你手边；把第一名往下拖时松手后再跳回顶部，反而会把刚放下的行甩出视野。

### 什么算「排到第一位」

同时成立才算：新旧顺序都有第一名且换人了；新第一名在旧顺序里已经存在；旧第一名在新顺序里还在。

- 宿主半部自己上浮：算。
- 另一个客户端（或桌面端）上的活动导致本机上浮：算。
- 在左侧栏里把某个工作区拖到第一位：顺序上算一次重排，但本地拖拽处在静默窗口里，不滚——行已经在你手边。

### 什么时候不滚

- **基线**：页面加载时控制器还在 `loading`，以及断线恢复后整份替换投影——第一份完整顺序不是「重排」，不滚。
- **新建工作区插到最前**：新 id 旧顺序里没有，不滚。
- **删除原第一名**：旧第一名消失、下一个顶上来，不滚。
- **改名、会话行变化**：顺序没变，不滚。
- **本地工作区拖拽**：拖拽期间与结束后 300ms 内不滚。
- **工作区分组不可见**：单列表视图（没有工作区分组）、搜索框有内容（列表被搜索结果替换）、侧栏收起成 rail、侧栏尚未渲染——这些情况下没有工作区分组行，不滚。
- **本来就在最上面**：`scrollTop` 已经是 0，不写。

## 什么不算「活跃」

以下情形看起来像活动，但都不触发上浮。

- **打开 / 恢复（resume）一个旧会话**：`session/created` 也会为它发一次，但插件按「是否已经在某个工作区的账下」判定它不是新建，因此不上浮。
- **subagent 子会话**：侧边栏本来就隐藏它们，创建、回合结束，以及它发起的审批 / 提问都不上浮。
- **被复用的空白会话**：同一个工作区里再点一次「新建会话」而复用了已有空白会话时，没有新会话产生、行上的时间也没变，所以不上浮。
- **Ungrouped 会话**：不属于任何工作区，没有可上浮的分组；它发起的审批 / 提问同样没有分组可浮。
- **没有 agent 的提问**：非 agent 作用域的 `user-questions/request` 没有会话可定位，插件只把请求放行。
- **审批策略为 `never` 的自动拒绝**：上游在进入应答链之前就返回拒绝，用户根本没收到卡片，插件也就不上浮。
- **工作区自身的变化**（改名、拖拽）：不是会话活动，不上浮；拖拽的滚动行为见上一节。
- **用户手动停止的回合**：`aborted` 的任一原因（用户取消、hook 取消、父级取消、会话销毁）既不算完成也不算报错。
- **策略阻断、token 上限截断**：`blocked`、`max-tokens` 都不属于「模型请求重试耗尽」。
- **工具失败、未知错误**：即便当前 step 的重试已到上限，带 `UNKNOWN` / `TOOL_ACTIVATION_FAILED` 合成码的失败也不算模型请求报错。
- **重试还没到上限的失败**：还有重试机会的失败不算耗尽。
- **没跑过 step 的空回合**：`completed` 但没有 step，没有最终回复，不算任务完成。

## 挂载与启用

两步：把新包记进 lockfile，再把包挂进 web profile。

```powershell
# 仓库根:把新包记进 lockfile(需要 pnpm 的 store 访问)
pnpm install

# 挂进 web profile(与其它本地插件同一入口;脚本会把本插件加进去)
./add-plugins.ps1
```

插件的两个半部：

- **宿主半部** `index.ts` 与 `src/bump.ts` 由 Node Type Stripping 直接加载，没有构建产物。
- **浏览器半部** `src/client.ts` 由 tsdown 打成 `lib/client.js`，由 `package.json` 的 `dsh.client.platform = web` 与 `exports["./client"]` 声明。仓库根的 `add-plugins.ps1` / `add-plugins.sh` 发现 `exports` 里写明、磁盘上还没有的 `lib/*.js` 时会先跑 `pnpm --filter dsh-workspace-activity-sort build`。

改浏览器半部后：`pnpm --filter dsh-workspace-activity-sort build` 重新构建，再重启 `dsh web` 让宿主重新合成启动图，页面刷新后加载新产物。宿主半部改动重启 `dsh web` 即生效。

没有配置项：插件不导出 `Config`，行为只有「会话活跃（含任务终点、等待用户）即上浮」与「有工作区被排到第一位即滚回最上面」两条。

## 实现要点

下面几条是实现上的关键取舍，也是排查顺序。

- **顺序的真源在宿主**：侧边栏 Workspace 分组的顺序是 Workspace 注册表的持久顺序（会话顺序存在浏览器本地，Workspace 分组的拖拽顺序由 Host 持久化）。插件把顺序写回注册表，所有消费方一次对齐。
- **依据用事件**：用户消息提交由 `api-session/activity` 给出，侧边栏会话行右侧显示的时间是同一事实(`max(会话创建时间, 最后一条用户消息时间)`)；任务终点读会话日志里的 `turn/end`，模型请求重试靠 `llm/retry` 计数；等待用户读两条 waterfall。插件不冷读会话历史、不维护活动时间表，也没有重启后需要恢复的状态。
- **任务终点的判定在纯函数里**：`taskOutcome`（`src/bump.ts`）只接收回合号、终止原因、当前 step 的重试记录与「是否跑过 step」，返回 `'completed'` / `'error'` / undefined，全部终止原因都由它一处裁决。
- **等待用户用 waterfall 观察，而不是读 `approval/asked`**：`approval/asked` 在策略 `never` 时也会落盘（随后被自动拒绝，用户没收到卡片），而 waterfall 只在请求真的交给应答链时才会被派发。观察者必须调用 `next()`，并且用 `prepend` 排在应答者前面，否则会被命中请求的应答者短路。
- **`llm/retry` 按结构读取**：该事件由 `@deepseek-ai/dsh-llm-retry` 追加到会话日志，插件只 `import type` 它的 `LlmRetryEventData`，不引入运行时依赖；字段不完整时宁可不判定，也不误判。
- **等待用户只用公开事件类型**：`approval/request` 与 `user-questions/request` 的类型来自两个 `import type` 依赖（`@deepseek-ai/dsh-user-approval/types`、`@deepseek-ai/dsh-user-questions/types`），运行时仍不需要这两个包。
- **重试记录跟着 step 走**：`step/start` 清空该会话的记录，`turn/end` 判定后清空，会话销毁时一并作废。
- **归属查询用注册表自己的账**：会话属于哪个工作区，读注册表实体的 `sessionIds`，不做 cwd 字符串匹配。
- **只用公开 API**：`workspaceRegistry.insertBefore(id, beforeId)` 语义同 DOM `insertBefore`（移到锚点之前）；「已经在最前」时它一次写盘都不做，插件也提前跳过，所以在同一个工作区里连续聊天不会反复写盘。
- **自己的写入不会触发自己**：重排只写全局顺序单例(`domain/changed` 的 `table` 为 `''`)，而插件只听工作区表(`table === 'workspaces'`)。
- **事件只入队，收敛排到宏任务**：监听器只入队并排一轮。这一轮延迟到下一个宏任务是必需的：工作区表的 `domain/changed` 在注册表实体快照换新之前就发出来了（持久写入 → 事件 → 实体换新），隔一个事件循环才读得到 attach 之后的归属。
- **滚动的判定也在纯函数里**：`frontArrival`（`src/scroll.ts`）只接收前后两份顺序，返回被排到第一位的工作区 id 或 undefined；哪些变化算、哪些不算由它一处裁决。`src/client.ts` 只订阅顺序、取出 id、订帧，并把 `scrollTop` 写入留给 `scrollWorkspaceSectionToTop`。
- **滚动只碰两个上游 `data-*` 锚点**：`[data-sidebar-list-area]`（滚动容器，上游 README 明确列为供测试与集成方定位的稳定标记）与 `[data-row-key^="workspace:"]`（分组行，用来排除单列表 / 搜索 / rail；上游没有把它写进稳定标记）。两者都写在 TSX 上、不是 CSS Modules 生成的类名；`check-css.mjs` 把它们对上游构建产物校验，上游改名时显式失败，而不是让插件静默不滚。
- **不在宿主发「我刚上浮了」的信号**：宿主半部只写顺序，浏览器只认顺序快照。本地拖拽、别的客户端、宿主自动上浮在快照里都是同一条 `order` 增量，所以两个半部之间不需要私有通道，也不会因为宿主半部缺席（例如只挂了客户端）而漏判。
- **滚动写入排到下一帧**：顺序增量先到、React 提交在后，隔一帧读到的才是新顺序下的 DOM；同一帧里的多条增量合并成一次写入。
- **断线恢复靠状态机识别**：控制器不提供「这是 baseline」的事件，插件读 `list.getSnapshot().state`：不是 `idle` 时把下一条通知标记为「等基线」，恢复后的第一条通知只更新 `previous`，不排滚动帧。
- **本地拖拽靠 document 捕获监听识别**：只认起点落在 `[data-row-key^="workspace:"]` 的 `dragstart`；`drop` / `dragend` 结束拖拽并开一个短静默窗口。`dragend` 丢失时（拖到页面外）`DRAG_STALE_MS` 兜底，避免一次丢失的事件永久停掉滚动。

## 边界

以下限制来自设计取舍或上游事实，不是缺陷。

- **只上浮，不做全量重排**：插件不会在挂载或重启时按历史活跃时间重排既有顺序，而是继承注册表当前的持久顺序；挂载之前发生的活动不会被追溯。
- **等待用户只在挂载后实时观察**：插件不追溯挂载前已经挂起的审批 / 提问；重连、刷新页面也不会重新上浮，因为请求只派发一次。
- **只要请求进入应答链就上浮**：由 ACP、SDK 等非 Web 客户端应答的审批同样触发一次；没有应答者时提问随后 fail closed，这一次上浮也保留（无害）。
- **任务终点只在挂载后实时观察**：插件不追溯挂载前结束的回合；挂载时正在进行的回合如果已经错过 `step/start`，它的结束不会被算作完成，报错判定同样依赖挂载后收到的 `llm/retry`。
- **重试上限来自 provider 配置**：默认 5 次；改成其它数字时判定随之变化，插件不写死这个数。
- **活跃由宿主事件决定，与是哪个客户端无关**：只有经过本宿主、被记为 `user/message` 的提交才算活动；别的 dsh 实例（或本插件未挂载时）写下的活跃不会体现在顺序里。
- 想固定某个工作区的位置，只能停用插件(没有 `pinned` 之类的配置)。
- 只排序 Workspace 分组；每个工作区内部的 Session 顺序不受影响。左侧栏切到「单列表」分组模式时没有分组可排，插件不产生可见变化；这种视图下也不会滚回最上面。
- 宿主注册表不可用时宿主半部不挂载(`inject: ['workspaceRegistry']`)；浏览器里的工作区控制器缺席时浏览器半部不挂载（客户端 `inject: ['workspaces']`）。两个半部互不依赖，缺席时各自降级。
- 同一毫秒登记的两个新会话，按会话 id 定序（确定性，但不保证与创建先后一致）。
- **滚动只到最上面，不定位到那一行**：工作区树模式下被排到第一位的工作区仍可能渲染在某个父工作区之下，第一名不一定出现在第一行；插件按「滚回最上面」实现，不做 `scrollIntoView`。
- **顺序快照分不清「别的行被拖上来」与「第一名被拖下去」**：本地拖拽有静默窗口，不会误滚；同一个变化如果来自另一个客户端（那边手动把第一名拖到后面），本机把它当成一次上浮，会滚一次。
- **断线期间的顺序变化不在恢复时补滚**：重连后的第一份顺序只当基线；断线期间别的客户端造成的上浮要等到下一次变化才会滚。
- **侧栏顶部导航不受影响**：滚回的是工作区区块自己的滚动条；如果侧栏 viewport 已经为露出内容把导航滚走，插件不会把导航拉回来。
- **滚动不做动画**：本地拖拽与断线恢复之外，任何客户端造成的「某个工作区被排到第一位」都会让本机列表滚回顶部；写入是直接的 `scrollTop = 0`，没有平滑滚动。
